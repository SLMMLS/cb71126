# Android, раунд 5: передача файлов с телефона на ПК и обратно

Что просили: быстро отправлять и принимать файлы по Wi-Fi между телефоном и ПК, не потеряв буфер обмена и
остальное. Протокол — `../PROTOCOL.md`, §3c; общая запись раунда — `../CHANGES.md`. **Схема базы Room не
менялась** (первое её изменение должно быть отдельным шагом, см. `ROADMAP.md`), **новых зависимостей Gradle нет.**

## Что добавлено

| Файл | Что делает |
|---|---|
| `files/FileProtocol.kt`, `FileNames.kt` | константы, запечатывание сообщений с привязкой к передаче и номеру куска, JSON-сообщения; очистка имён файлов (близнец Rust-функции, общий список проверок) |
| `files/FileReceiver.kt` | **приём**: offer → куски → finish; временный файл, докачка, повторы без дублей, отмена, лимиты, проверка SHA-256, «нет места» до начала |
| `files/FileSender.kt` | **отправка** на ПК: offer, недостающие куски, finish; повтор при сбое сети с паузами 1/2/4/8/15 с, понятные тексты отказов |
| `files/TransferManager.kt` | очередь (один файл за раз), «Отменить»/«Повторить», включение и выключение службы без гонок |
| `files/TransferModels.kt` | строка списка передач; список (с расчётом скорости) и его сохранение в `files/file-transfers.json` (не в Room) |
| `files/PublicDownloads.kt` | куда кладётся полученный файл: «Загрузки/ClipSync» через MediaStore (Android 10+); на Android 9 — папка приложения |
| `files/FileSources.kt`, `OkHttpFileTransport.kt`, `FilesSettings.kt` | чтение файлов по адресу `content://` (никогда `file://`), копия для «Поделиться», транспорт OkHttp с закреплённым сертификатом, переключатель приёма |
| `files/Transfers.kt`, `TransferService.kt`, `TransferNotifications.kt` | сборка всего в одном месте (создаётся в `ClipSyncApp`), служба переднего плана на время отправки, уведомления о ходе и о полученном файле |
| `ui/FilesScreen.kt` | экран «Файлы»: отправка, список, «Открыть», «В Загрузках», «Повторить», «Убрать» |
| `share/ShareFileActivity.kt` | «Поделиться» → «Файл на ПК» (отдельный пункт, существующий «Отправить на ПК» для текста и картинок не тронут) |
| `network/PcFeatures.kt` | что ПК сообщил о своих возможностях (в SharedPreferences) |

Правки в существующем: `network/Protocol.kt` (возможность `files` в списке), `network/HelloSender.kt` (запоминает
ответ ПК о возможностях), `network/SyncServer.kt` (маршруты `/file/*`; нестандартные коды 422/423/507 через
собственный `IStatus`), `network/SyncClient.kt` (клиент для файлов: один на передачу, чтобы соединение
переиспользовалось), `service/ReceiverService.kt` (подключает приёмник к серверу), `data/Repository.kt`
(отвязка ПК останавливает передачи), `ui/MainActivity.kt`, `ui/HomeScreen.kt` (кнопка «Файлы»),
`ui/SettingsScreen.kt` (переключатель «Принимать файлы с ПК»), `AndroidManifest.xml` (служба, пункт в «Поделиться»).

## Решения, которые стоит знать

1. **«Поделиться» делает копию файла в кэш.** Доступ, который даёт «Поделиться», живёт, пока открыт экран-получатель,
   а передача (с повторами) длиннее. Копия удаляется после успешной отправки, при «Убрать» и через сутки при запуске.
   Файлы из выбора на экране «Файлы» читаются на месте (доступ просится «запомнить»); если приложение-источник не
   сообщает размер, делается копия — протоколу размер нужен до начала.
2. **Служба `TransferService` имеет тот же тип `connectedDevice`, что и приёмник**, поэтому новых разрешений
   нет. Если Android 12+ откажет в запуске службы из фона, передача идёт дальше, пока система позволяет процессу жить.
3. **Принятый файл хранится дважды на мгновение** (временный и копия в «Загрузках»), поэтому свободное место
   проверяется с запасом в два раза.
4. **Пункт «Файл на ПК» виден при любом «Поделиться»**, в том числе при шаринге текста (манифест не умеет «только если
   есть файл»); для текста он подсказывает правильный пункт.
5. **Программы и установочные файлы** (`apk`, `exe`, `bat`, `sh`…) сохраняются, но «Открыть» для них нет.

## Что проверено и что нет

* **[K]** компиляция `kotlinc 2.0.21` всех не-экранных файлов приложения и новых экранов против настоящего `android.jar`
  (API 34), BouncyCastle и настоящего NanoHTTPD 2.3.1; Compose, Room, OkHttp, AndroidX заменены заглушками
  с сигнатурами по памяти (Material3 1.3, OkHttp 4.12). Так нашлась и исправлена одна настоящая ошибка:
  в `SyncServer.kt` не хватало импорта `Response` для нового кода вне класса.
* **[K]** 65 тестов логики на JVM (`jvm-tests/run.sh`): имена (44 общих проверки с Rust), запечатывание, приём
  (докачка после перезапуска, дубли, подмена куска, неверный хеш, отмена с обеих сторон, лимиты), отправка по
  настоящему HTTP, очередь (в том числе 40 потоков одновременно). **[мутации]** 8 из 8 поломок ловятся.
* **[K↔R]** настоящий Kotlin-код ↔ настоящий Rust-код по сокетам, в обе стороны, байт в байт (`../tools/cross-test.sh`).
* **Не проверено:** сборка Gradle и запуск на телефоне. В частности: экраны Compose против настоящей библиотеки,
  MediaStore (создание файла в «Загрузках»), служба на Android 14, уведомления, меню «Поделиться», работа
  OkHttp с закреплённым сертификатом на 1 МиБ-запросах, скорость на реальном Wi-Fi. Если сборка Gradle не пройдёт,
  первая подозреваемая — `ui/FilesScreen.kt` (сигнатуры Compose) и `files/PublicDownloads.kt` (MediaStore).

# Android, раунд 4: выключение приёма и «я в сети»

Что просили: приложение закрывали, а оно продолжало работать, и остановить его было нечем; плюс сообщение
«я в сети» (предложено в раунде 3). Схема базы Room **не менялась**, новых зависимостей нет.

## Выключение приёма

Приёмник работает как служба переднего плана, чтобы ПК мог присылать записи в любой момент, —
поэтому закрытие приложения его не останавливало. Теперь есть три способа:

1. **Кнопка «Выключить» в уведомлении «ClipSync активен»** (широковещание `StopReceiver`; остановка службы
   всегда разрешена системой, в отличие от запуска).
2. **Переключатель «Приём»** в верхней панели главного экрана и в «Настройки → Приём с ПК».
3. **«Останавливать при закрытии приложения»** (там же, по умолчанию выключено): смахнули приложение из
   недавних — приём остановился (`onTaskRemoved`), открыли — включился. Сам переключатель при этом не трогается.

Пока переключатель выключен, приём не включают ни открытие приложения, ни перезагрузка телефона
(`BootReceiver`); после перезагрузки приём не возвращается и при включённой «остановке при закрытии» —
этот режим означает «принимаю, пока пользуюсь». Свежее сопряжение переключатель включает снова.
Отправка с телефона на ПК («Поделиться», «Отправить на ПК») от приёма не зависит и работает всегда.
При выключении ПК получает сообщение «приём выключен» (см. ниже) и перестаёт слать и копить записи.

## «Я в сети» (`POST /hello`, PROTOCOL.md §3b)

Телефон сообщает ПК адрес, порт, версию протокола, возможности и то, слушает ли приёмник: при запуске
приёмника, при смене сети или адреса (`NetworkWatcher`), при открытии приложения, при выключении приёма и по
кнопке «Проверить связь». `HelloScheduler` склеивает пачки событий, не шлёт чаще раза в 15 с, повторяет
неудачу через 3, 10 и 30 с и бросает; срочные запросы (выключение/включение) идут сразу. Если часы телефона и ПК
расходятся больше чем на 5 минут, ПК отклоняет сообщение, а «Проверить связь» говорит об этом прямо.

## Новые и изменённые файлы

`service/ReceiverControl.kt`, `service/StopReceiver.kt` (новые); `network/HelloScheduler.kt`,
`network/HelloSender.kt`, `network/HelloState.kt`, `network/NetworkWatcher.kt` (новые); `service/ReceiverService.kt`,
`boot/BootReceiver.kt`, `network/Protocol.kt`, `network/SyncClient.kt`, `data/Repository.kt`, `ui/MainActivity.kt`,
`ui/HomeScreen.kt`, `ui/SettingsScreen.kt`, `AndroidManifest.xml` (изменены).

## Проверка и её границы

Проверено: ядро (20 файлов: служба, сеть, данные, криптография, автозапуск) и `SettingsScreen.kt`
компилируются настоящим `kotlinc 2.0.21` против настоящего `android.jar` (API 34) и BouncyCastle, с
заглушками Room/OkHttp/AndroidX/Compose/корутин; логика `HelloScheduler` и `describeHello` — на JVM; формат
сообщения `/hello` — настоящий Kotlin-код против настоящего Rust-кода ПК (ключи, шифрование, имена полей).
Не проверено: Gradle-сборка с настоящими библиотеками и работа на устройстве (жизненный цикл службы, кнопка в
уведомлении, `onTaskRemoved`, системные сетевые события). Правки в `HomeScreen.kt` и `MainActivity.kt` — несколько
строк по образцу соседнего кода; полным набором заглушек Compose они не проверялись.

# Android: что изменилось (версия 0.2.2)

Основа — `android2` из присланного архива (моя версия + ваш `android.yml` и `-opt-in` для Material 3).
Папка `android` (исходник) не менялась.

| Что | Зачем | Проверка |
|---|---|---|
| Список без чтения содержимого (`EntryMeta`), содержимое читается кусками по 512 КБ | Android читает результат запроса через CursorWindow ≈2 МБ: одна строка с BLOB крупнее (любой нормальный скриншот) ломала `SELECT *` всего списка | SQL проверен на SQLite: 5 МБ ↔ 10 запросов, побайтно равно |
| Миниатюры картинок в списке; кэш (16 МБ) и декодирование вне главного потока | Картинки отображались словом «Изображение» | `kotlinc` + типизация UI |
| Предпросмотр записи (`EntryScreen`): текст (выделяется), картинка (масштаб/сдвиг) | Нет способа посмотреть запись целиком | типизация UI |
| Вкладки «Все / Телефон / С ПК», кнопка «→» у каждой записи | Нужно выбирать, что отправить, а не только «последнее» | типизация UI |
| Захват буфера телефона при открытии приложения (`captureClipboard`), дедупликация по хэшу, подрезка до 300 | История того, что скопировано на телефоне | логика на JVM: 30 проверок (индекс, превью, масштаб, PNG-заголовок) |
| Дубли с ПК не плодятся: повтор поднимает запись наверх, без второго уведомления | ПК повторно присылает то, что вы заново скопировали | `kotlinc` |
| «Отправить на ПК» в меню выделения текста (`PROCESS_TEXT`) | Отправить точно нужный кусок без копирования | XML валиден; сборка у вас |
| Переключатель «Запоминать буфер при открытии» | Android 12+ показывает «вставил из буфера» при каждом чтении | — |
| Общие утилиты изображений (`ImageUtils`) для «Поделиться» и буфера | Один код вместо двух; лимиты размера/стороны | JVM |
